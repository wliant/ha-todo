# 0051 - A tracker is its own aggregate, and the third one

Status: accepted
Date: 2026-11-19

## Context

Requirements 0019 adds **trackers**: a number a household records against a
bucket, over and over, so it can see the shape it makes (R159-R172).

There are two existing aggregates it could have been bolted onto, and both
readings of it are wrong in a way that is worth writing down, because both look
cheaper than what we did.

**A tracker is not a todo list with a numeric cost.** `list_field` already
declares a NUMERIC cost with a unit and a points rate (adr/0011), so "weight in
kg" is expressible. But a cost is a property of *a chore that was done*: it
hangs on a `todo_item`, which carries an assignee, a due date, a completion and
a points award, and `TodoListService.create` writes a `DESCRIPTION` and a
`DUE_AT` field row for every list it creates (adr/0022). Recording a weight
would mean inventing a chore to hang it on, which the dashboard would then
offer somebody tomorrow morning, the recurrence job could generate, and the
leaderboard would score.

**A tracker is not a collection with numeric entries either.** `data_entry` is
closer - no assignment, no completion - but its whole shape is a document:
`search_vector` is a generated `tsvector` fed by `detail_text` and `tags_text`
(adr/0033), indexed with GIN and ranked with `ts_rank`. A tracker has no text
to index. It would carry a search apparatus over a column of digits, and an
entry would need a nullable amount and a nullable bucket that mean nothing to
any other entry in the table.

Behind both is adr/0029's argument, which does not weaken with repetition: a
`kind` discriminator makes every existing reader of the table responsible for
remembering that a new thing exists, and the reader that forgets **compiles,
passes, and is wrong**. `todo_list` had nine such readers when 0006 was
written; it has more now.

## Decision

A tracker is its own aggregate, and the product now has **three**.

New tables `tracker`, `tracker_access`, `tracker_reading`, `tracker_user_state`
and `tracker_interaction_day`; a new `com.hatodo.tracker` package with its own
repositories, services, controllers and exception advice. No `kind` column on
`todo_list` or on `data_list`, and no tracker row reachable from any existing
query.

`TrackerService` carries a third deliberate copy of the same two predicates -
`readable` (owner, or a grant row; absent answers **404**) and `managed`
(owner, and still not `|| isAdmin()`, for adr/0010's reason). `ListIcon` is
shared, because it is a closed set of drawings with no behaviour. Nothing else
is.

A tracker has **no `stored_image` owner column**. A reading's note is plain
text, so there is no claim pipeline, no sanitizer and no fourth nullable owner
FK - which matters because adr/0032 set the threshold for replacing that
column shape with a join table at exactly the fourth owner.

## Consequences

Every existing read of `todo_list` and `data_list` is correct without being
changed, and stays correct when somebody adds the next one. A tracker cannot be
assigned, completed, scored, searched as a document or generated by the
recurrence job, because there is no column to put any of that in.

The cost is a third copy of roughly 150 lines of access plumbing the repository
has now written three times, plus a third grant table, a third pin table and a
third interaction bucket. `TrackerServiceTest` carries the same guard
`DataListServiceTest` does - create writes the owner's grant row **and nothing
else** - as the test that fails if the discriminator design creeps back in.

**"Everything the member can see" now has three answers**, and anything written
from here that reads across a member's things has to say which it means. That
is a real cost and it is paid in attention: the schema makes the *wrong* answer
impossible, not the ambiguous question.

**At a fourth kind, re-examine rather than copy.** Three copies of a predicate
is duplication with a reason; four is a pattern that should have been
extracted, and the same is true of `web/src/app/repin.ts`, whose envelope
branch now names three arrays by hand.

## Alternatives considered

- **`kind` on `todo_list`** - rejected for adr/0029's reasons, which apply with
  more force now that there are more readers.
- **`kind` on `data_list`, with nullable `amount` and `period_start` on
  `data_entry`** - the tempting one, because collections already lack
  assignment and completion. Rejected: the search index is the point of that
  table, half its columns would be permanently null on one kind, and
  `DataEntrySearchQuery` would have to learn to exclude a row type it cannot
  rank.
- **A generic "measurement" service over the existing field machinery** -
  rejected as the most expensive option: it would couple the tracker's shape to
  `list_field`, whose merge-on-id semantics exist to protect item costs that
  trackers do not have.
