# 0007 - Installable PWA without offline caching

Status: accepted
Date: 2026-11-04

## Context

R13 asks for an app that installs to a phone's home screen and opens standalone.
Offline use is explicitly out of scope, in 0001 and again in 0003.

The two pull in opposite directions in practice. "Make it a PWA" is usually
delivered by a toolchain plugin (`vite-plugin-pwa` and Workbox) whose default is
a precache manifest: every hashed asset and `index.html` are cached and served
cache-first. That default would actively hurt here. nginx deliberately serves
`index.html` with `no-store` so a deploy cannot leave a family member booting a
stale bundle; a precaching service worker reintroduces exactly that staleness in
a layer the deploy cannot reach, and the usual fix is a prompt-to-reload UI that
nobody asked for.

A service worker is still wanted: Chrome's install criteria include one with a
fetch handler, and without it the install prompt is not offered on desktop and is
degraded on Android.

## Decision

Hand-write the PWA surface - `public/manifest.webmanifest`, the iOS meta tags in
`index.html`, generated icons - and ship a service worker that caches **nothing**.
`public/sw.js` has a fetch handler that passes through to the network, and
`skipWaiting` / `clients.claim` so a new one takes over immediately.

No PWA toolchain plugin. Icons are generated by a committed script
(`web/scripts/generate-icons.mjs`) using Node's built-in `zlib`, with the PNGs
committed alongside it.

nginx serves `sw.js` and the manifest with `Cache-Control: no-store`, for the
same reason `index.html` is uncached.

## Consequences

- The app installs, is titled "List", and opens standalone on Android and iOS.
- Freshness behaviour is identical installed and in a browser tab, and a deploy
  is still the only thing that decides which bundle runs.
- The app does **not** work offline, and opening it without a network shows the
  browser's own failure. That is the stated requirement, not an oversight.
- The service worker is nearly empty, which looks like dead code. The comment in
  it says why it exists, or someone will delete it and silently lose
  installability.
- If offline use is ever wanted, this is the file to change, and it needs its own
  ADR - a caching strategy must answer the `index.html` staleness question that
  nginx answers today.
- Icon changes mean running the generator and committing its output, rather than
  dropping in a PNG from a design tool. Acceptable: the icon is a checkmark.

## Alternatives considered

- **`vite-plugin-pwa` with `injectManifest` and no precache.** All of the plugin
  and none of its value; the service worker would still be hand-written, with a
  dependency and a build step on top.
- **`vite-plugin-pwa` with its defaults.** Rejected on the staleness grounds
  above.
- **No service worker at all.** The manifest alone is enough for Android's "add
  to home screen" and for the share target, but loses the install prompt. Cheap
  enough to keep the empty worker.
- **A committed PNG from a design tool.** Nothing to reproduce it from, and the
  512, 192 and maskable variants drift apart by hand.
